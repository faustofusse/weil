## Inspecting a user's database

`bun scripts/db.ts --ls` lists the app's users (id / name / email / db name, from the auth worker's D1); `bun scripts/db.ts <user> --tables|--schema|"select ..."` reads that user's Turso DB, where `<user>` is an id, email or display name (`--json`, `--width=N` for wide cells). Resolution and token minting live in `scripts/turso.ts` (auth D1 lookup + Turso platform token, taken from `TURSO_API_TOKEN` or the logged-in `turso` CLI), shared with `scripts/import-*.ts` and `prueba-jev/lib/db.ts` so the hostname is never hardcoded again. Two limits are inherent, not missing features: it is **read-only** (the phone owns the transaction boundaries and the undo, and the sync engine would replicate any damage to every paired device), and it sees the **server** copy only — rows still unsynced on a device are invisible, which is why `Reconcile.kt` and `SuggestRepository`'s retrieval run on-device. `pragma user_version` is per-file and not replicated (the server always answers 0), so `--schema` prints columns: whether a migration landed is answered by the column existing.

## Architecture

Auth is passkey-based via the auth worker in `/Users/fausto/sw/auth` (deployed at https://auth.fausto.ar, app slug `finance`, rp domain `finance.fausto.ar`). Flow: `AppGraph` (commonMain) wires `AuthRepository` (login→fallback register via `PasskeyCeremony`), `DatabaseProvider` (jwt → `session/refresh` on `401`/`unauthorized` in error text → re-login on 401), `AccountsRepository` and `NotificationsRepository`. Each user gets their own Turso DB provisioned by the worker (libsql-type on Turso Cloud); local synced databases live at `databases/{userId}/turso.db` (Android filesDir, iOS Documents) on the new Turso sync engine on **both** platforms — libsql-swift is gone. Tokens + the `auth_finance` refresh cookie are in secure storage (EncryptedSharedPreferences / iOS Keychain via the Swift `KeychainStore` bridge). iOS passkey ceremony + secure store are Swift (`PasskeyManager.swift`, `KeychainStore.swift`) injected into `IosBridges` before `MainViewController()` runs; `AppGraph` takes `passkeys: () -> PasskeyCeremony` lazily (Android builds the ceremony around the foreground activity only when sign-in starts).

Auth is passkey-based; Android `WeilApplication` (app class in the manifest) owns the single `AppGraph` shared by `MainActivity` and the notification listener service (`AndroidGraphHolder`). `AppGraph` exposes `accounts` (`AccountsRepository`) and `ledger` (`TransactionsRepository`) for the double-entry bookkeeping layer.

- UI (sharedUI commonMain): Navigation 3 KMP (`org.jetbrains.androidx.navigation3:navigation3-ui`) with a plain `mutableStateListOf<Any>` back stack and the slide/fade transition specs. Theme: the catalog is the `AppTheme` enum in `AppTheme.kt` (one entry = one complete M3 `ColorScheme`; adding/swapping a theme touches only that file); `Theme.kt` holds `AppThemeState` + `LocalAppThemeState` (runtime swap with one assignment) and `FinanceTheme(theme)` wraps all of `RootScreen`, splash included. - Schema: single `SCHEMA_SQL` const in commonMain `Schema.kt`, applied idempotently on every open on both engines, followed by `migrateSchema()` for non-idempotent column additions. Both are skipped when `pragma user_version` already equals `SCHEMA_VERSION`, so **any change to `SCHEMA_SQL` or `migrateSchema()` must bump that constant** — forgetting it is invisible on the device that wrote the migration (its database was migrated while the version still differed) and fatal everywhere else, which is how `accounts.in_net_worth` shipped to iOS as "no such column". Tables: `accounts(id, name, parent_id, type)`, `transactions(id, date, payee, note, source_notification_id, source_email_id, created_at)`, `postings(id, transaction_id, account_id, amount_minor, commodity)`, `transactions.source_document_id` (R2 hash of an AI-imported document), `embedding`/`embedding_model` on `transactions`, `notifications` and `emails`, `transaction_sources(transaction_id, kind, ref, event_key, created_at)` (many-to-many provenance — one event arrives through several doors; the legacy single-valued `source_*` columns are still written and are backfilled into it idempotently), plus `notifications`, `applications`, `emails`, `suggestions(id, kind, ref, event_key, candidate, created_at)` (`unique(kind, ref)`; **unused** since notifications started recording themselves — kept in `SCHEMA_SQL` because dropping a synced table is the one migration that is not free), and `settings(key, value, updated_at)` (synced scalar preferences — the secure store is device-local and holds tokens only; row-level LWW is the right merge for a scalar). All timestamps are epoch **ms** — the email worker (`app/worker`) writes `emails.received_at` server-side, so it must also use ms (`Date.now()`), and SCHEMA_SQL carries an idempotent seconds→ms migration for older rows. No device_id/modified_at/deleted_at/synced_at columns — the Turso engine replicates row state (incl. deletes) between devices. `migrateSchema()` also seeds default accounts **only when the accounts table is empty** (never resurrects user deletions): "External" expense and income accounts with fixed ids `EXTERNAL_EXPENSE_ID`/`EXTERNAL_INCOME_ID` (fixed ids so two concurrently-seeded fresh devices converge on the same synced rows) — these are the fallback defaults in `TransactionQuickScreen` (gasto category / ingreso source), matched by `EXTERNAL_ACCOUNT_NAME`, and are also seeded as the initial rows of `settings` on a fresh database.
- Default accounts: `SettingsRepository` (sharedLogic commonMain) stores one account id per `AccountType` under `default_account.<type>`; `resolveDefault(tree, type, stored)` turns a stored id into a usable pick, validating it against the live tree (an account deleted on another device degrades to the old heuristic instead of dangling) and deliberately refusing to guess a category — for income/expense, with no seeded "Otros" and more than one candidate it returns null so the user picks, while for asset/liability a wrong guess is visible and one tap to fix. Set from `AccountActionsSheet` (long-press an account → "Usar como predeterminada", a toggle), shown as a star in `NodeRowView`, held in `LedgerState.defaultAccounts`, and consumed by `TransactionQuickScreen` and `ImportReviewScreen` (screen-wide default account + fallback category). `AccountsRepository.delete` drops a `default_account.*` row pointing at the deleted id.

- Document import (AI): the user shares an image/PDF into the app (Android `ACTION_SEND` filter on `MainActivity`, `singleTask`; `handleSharedDocument` reads the `content://` stream and parks it in `SharedImportInbox`, which `RootScreen` replays once composed and signed in) or picks one from Home's overflow (`DocumentPicker` — SAF on Android, `UIDocumentPickerViewController` via `DocumentPickerManager.swift` on iOS, AWT `FileDialog` on desktop; resolved lazily like `QrScanner` because it needs a foreground activity). `ImportRepository.analyze` POSTs the raw bytes to the finance worker (`api.finance.fausto.ar/import/analyze`) with the same `auth_finance` cookie the auth worker issues — the worker re-implements `requireAuth` against the shared `AUTH_DB`, so revocation/expiry are free. The worker stores the file in R2 (`finance-docs`, key `{userId}/{sha256}`, readable back via `GET /import/document/{docId}`), loads the user's postable accounts from their Turso DB (**parents included** — the tree is organizational and postings may reference any node, so filtering to leaves silently hid "Comida" as soon as it grew a "Comida:Verduras" child; expense/income as categories **and** asset/liability as payment methods, so "Forma de Pago: Dinero disponible en Mercado Pago" resolves to the user's own Mercado Pago account — per-candidate `accountId`, falling back to the review screen's default account), and calls **Gemini** with `responseSchema` structured output — through the account's AI Gateway, falling back to the Google API directly when the gateway answers with an `AiGatewayError`. `GEMINI_MODELS` is an ordered list (`gemini-3.5-flash,gemini-3.6-flash,gemini-3.5-flash-lite`): a 503/429 "high demand" on one pool moves to the next model rather than retrying the same one, which can stay congested for minutes. It returns candidates only; `ImportReviewScreen` (compact rows, tap to expand and edit payee/amount/category, checkbox to approve) writes them in one SQL transaction via `TransactionsRepository.addAll`, tagged with `source_document_id` and undoable from the Snackbar; the screen-wide default account (used only for rows the document didn't attribute to one of the user's own accounts) seeds from the mode of the candidates' detected accounts, a lone candidate opens pre-expanded, and `imePadding()` sits on the `Scaffold` (not the inner content) so the sticky bottom bar rides above the keyboard. Analysis of a one-page statement takes ~15–25 s, so `ImportRepository`'s client installs `HttpTimeout` with a 180 s budget (the default socket timeout kills the call otherwise). Gotchas: `gemini-2.5-flash` is retired for new API keys; the screen depends on the `DocumentAnalyzer` interface so the desktop shot harness can inject `FakeImportAnalyzer` (`./gradlew :app:desktopApp:shot -Pshot.route=import`).
- Reconciliation (`Reconcile.kt`, **sharedLogic commonMain, pure functions** — see `docs/reconciliation.md`): the same economic event reaches the app as a statement row, a push notification, an email receipt or a manual entry, so every producer maps to one source-agnostic `CandidateEvent` (signed amount from the owner's point of view) and `matchAll` (batch entry point; `matchEvent` is the single-event one, and the batch pass additionally guarantees **one stored transaction is claimed by at most one event** — four identical `Anomaly -21,23` statement rows otherwise all stacked onto the same ledger row) tiers it against a window of `LedgerFact`s loaded by `TransactionsRepository.reconcileFacts(from, to)` — `Confident` / `Ambiguous` / `None`, with relations `AlreadyImported` (the `event_key` fingerprint is already attached), `Duplicate` (same own account, same sign) and `Mirror` (the other half of a transfer: opposite sign on another own account, whose dangling expense/income leg gets repointed on association). The matcher deliberately lives in Kotlin, not the worker: the notification listener is offline-capable and matches rows that have not synced yet, and the worker only ever sees *server* Turso state. `ImportReviewScreen` syncs before uploading, then offers every row as crear / asociar / omitir with the `MatchReason`s spelled out (the enum is translated in the UI so sharedLogic stays untranslated); writes go through `addAll` (creations, with their source rows) plus `TransactionsRepository.associate` (attachments), both undone together from one Snackbar via `revertAssociations`. `TransactionDetailScreen` lists every origin of a row (`ledger.sources(id)` → `StoredSource`), which is what makes the many-to-many `transaction_sources` visible to the user.
- Live category guess (`CategorySuggestRepository.kt` + `app/worker/src/suggest.ts`): while the description is typed in the create panel (`TransactionSheet` — the one the FAB raises over Home; the older routable `TransactionQuickScreen` carries the same wiring), a **Choice** question to TypeSafe's Jev (`POST /suggest/category` on the finance worker, same `auth_finance` cookie, `TYPESAFE_API_KEY` secret) moves the category picker. It is a Choice over the user's **own** account paths plus an explicit "Ninguna de estas categorías", so the answer is always an account that exists or nothing — there is nothing to validate on the way back. The **app sends the candidate list** (it already holds the tree, and a per-keystroke Turso read would double the latency); the worker only spends the key. Debounce is the `LaunchedEffect` key on the description: a keystroke cancels the in-flight call, so a stale answer can never land on text the user moved past (450 ms, min 3 chars, `ImportDirection.Income` flips the question to "which income source"). The guess only ever moves a pick the user has not made — the first manual touch of the category field sets `categoryTouched` and guessing stops for the rest of the entry — and **there is no confidence threshold**: confidence measures how concentrated the distribution is, not whether the top option is right, and picks at 22% were observed correct (a spread-out answer means plausible neighbours, and the alternative is a seeded default nobody chose). What gates the feature is the question itself — the Choice carries an explicit «ninguna de estas categorías», so the model declines instead of guessing, and one tap overrides. The confidence is still printed under the row (`confianza 62%`) as the explanation for a row that moved on its own. Category paths there use `ROUTE_ARROW`, the journal rows' separator. Every failure (no session, no network, 502, timeout) is swallowed into null: a background guess must never throw the user out of a half-filled screen, which is why this repository does not raise `SessionExpired`. Measured with `bun scripts/suggest.ts` in `prueba-jev` (which imports the worker's own `categoryQuestion`, so the harness cannot drift from what ships): 19/20 on an es-AR table, p50 313 ms, p90 435 ms. Desktop harness: `FakeCategorySuggester` (substring matching, non-semantic) — `./gradlew :app:desktopApp:shot -Pshot.route=new` (the harness cannot type, so seeing the hint means seeding the `description` state by hand).
- Notification → transaction lab (`SuggestRepository.kt` + `app/worker/src/message.ts` + `handleSuggestAccounts` in `suggest.ts`, plan in `plans/notificacion-a-transaccion.md`): the flask icon in the top bar of `NotificationDetailScreen` **and `EmailDetailScreen`** opens **Probar sugerencia** (`SuggestDebugScreen`, `SuggestDebugRoute`), which runs the whole proposed path over one captured alert and shows every input and output (`SuggestDebugScreen`, `SuggestDebugRoute`) — it writes nothing and navigates nowhere, because the point is to watch the pipeline before it is allowed to propose a ledger row. Three stages: a **reader** turns the message into amount/direction/payee plus a `normalized` plain sentence (`POST /suggest/message`), through the account's AI Gateway with `google/gemini-3.5-flash-lite` first and `@cf/zai-org/glm-5.3-flash` behind it, falling back to Google directly if the binding itself is down — every one of these models reasons out loud unless told not to, which is where their seconds and tokens go (`thinking`/`chat_template_kwargs`/`reasoning_effort` all sent, since each family spells it differently); measured in `prueba-jev/scripts/readers.ts` over 16 real captures, the **device** does the retrieval (`EmbeddingsRepository.similarToText(normalized)` for precedents in `notifications` and `transactions`, `reconcileFacts(±20 h)`, `matchEvent`), and **Jev** picks accounts from closed lists (`POST /suggest/accounts`: `is_movement`, `direction`, `my_account`, `transfer_destination`, `expense_category`/`income_category` — which are literally `categoryQuestion()` with a notification-shaped `context`, same definition the typing screen and the WhatsApp bot use — plus `already_recorded`/`duplicate_of`). The split into two calls is deliberate: the retrieval must see rows that have not synced yet, which the worker never can. **No regex anywhere in this path** — reading "$ 12.400" vs "12.400 ARS" is language and belongs to Gemini, the same call the WhatsApp reader makes. Both endpoints are cookie-authed, read nothing from Turso (the device sends the tree) and write nothing; `?debug=1` echoes the prompt/`state`/`questions` and the raw provider response, which is what the screen renders. It is the second of two screens: the flask icon opens **Fuentes** (`SuggestSourcesScreen`, `SuggestSourcesRoute`) — the raw vector neighbours across the three embedded tables (notifications, emails, transactions) with their link buttons and a «Probar sugerencia» button that runs the pipeline and opens the trace — and a manual link from there is a labelled example. The detail screen itself shows **transacciones relacionadas** instead: the rows that already carry the notification as a source (`transactionsForSource`), rendered with the journal's `TransactionRow`. Both bench screens are source-agnostic: `SuggestSourcesRoute`/`SuggestDebugRoute` carry an `EventSource`, `SuggestSourcesScreen` reads its neighbours from that door's `EmbedKind` and writes provenance of that kind, and `SuggestDebugState` keys its cached traces by door **and** id (the two tables have separate id spaces, and a trace shown under the wrong message is the one bug a bench must not have). Desktop harness: `FakeSuggestTracer` (canned model answers, **real** retrieval over the seeded database) — `./gradlew :app:desktopApp:shot -Pshot.route=suggest` (`suggest-email` / `suggest-email-trace` for the mail side). The pipeline is **source-agnostic**: `traceNotification`/`traceEmail` both build one `TracedMessage` (source, ref, origin, title, text, at) and run the same three stages — an email's text is `emailPlainText(body_html ?: body_text)` capped at 4 kB (a receipt states its total in the first screenful; the rest is footer billed by the token), and the neighbour search stays within its own kind (`EmbedKind.Email` for mail) because the question is "what did I do last time *this template* arrived" and templates do not cross doors. The same pipeline runs **silently on arrival and writes the transaction** (`AutoRecordRepository.kt`): the notification listener fires it for every capture (own package excluded, reposts within 10 min collapsed by content, runs serialized on a Mutex) and `autoRecord.apply(source, ref, trace)` records what it read. Emails have no listener — the worker writes them into Turso server-side and the device only meets them on a sync — so they are found by `sweepEmails()`, fired once per sign-in from `RootScreen`: sync, then read the rows after a **watermark** in `settings` (`autorecord.email_watermark`, synced so a second device does not pay for the same mail; a fresh install starts at yesterday, never at the beginning of the mailbox), 25 rows per sweep, advanced row by row so a sweep cut short by a dead network resumes where it stopped, and gated by `hasAmount` — the same currency-anchored prefilter the embedding sweep uses, which decides not whether the mail is a movement (that is the reader's job) but whether it is worth two model calls. There is no inbox and no banner — a bank push is already the bank saying what happened, and the confirmation queue was the part nobody opened; the row lands in the journal like any other and is edited like any other. `planAutoRecord()` (pure, tested in `AutoRecordTest.kt`) is the whole rule: `worthRecording()` first (promotions, unreadable amounts and `AlreadyImported` matches write nothing), then a **`Confident`** match attaches the message as one more origin of the transaction that already records it (repointing the dangling leg on a `Mirror`) while **`Ambiguous` creates anyway** — a visible duplicate can be deleted, a silent merge takes money out of an account balance and nobody notices. Unattributed fields degrade rather than block: the own account falls back to the stored default (`resolveDefault`) and the category to the default/seeded «External», including for a transfer whose destination the model could not name, because a wrong category is visible and one tap to fix while a drifting account balance is not. Ids the trace names are re-checked against the live tree before posting, and the ref is checked against `transaction_sources` first so a re-captured alert is a no-op. A **transfer** posts to the reader's `destination` (an own account, validated in the worker and never the one the money left) when Jev's `transfer_destination` is not sure; that is how a cash withdrawal lands in the user's cash account instead of a spending category. The reader and Jev both get the user's `profile.name` (`PROFILE_NAME_KEY`), which is what tells a cash order "for FAUSTO" (a transfer into their own cash) from the same template addressed to someone else (an expense): measured 6/6 both ways with the name and 0/6 on the third-party case without it. **No account, bank or person names in these prompts.** Rules speak of kinds of account ("one that holds physical cash") and the model maps them onto the user's list. The limit is that an account whose name says nothing about cash is not found until one row has been fixed by hand; precedents now carry `from`/`to` account paths read from the ledger, so that fix teaches the next run. A run whose movement would exactly cancel an expense/income row from the same counterparty on the same account within the hour is skipped (`findReversal`, see `docs/reconciliation.md`). Each run prints one `auto-record …` line with the reader model and every model's answer (`SuggestTrace.logLine()`). The reader cases, including the cash-order ones, are in `prueba-jev/data/readers.cases.json`; run `bun --env-file=.env scripts/readers.ts --case cash- --only gemini-3.5-flash-lite`.
- Similarity search (`EmbeddingsRepository.kt` + `app/worker/src/embed.ts`, plan in `plans/similares-en-la-app.md`): one `F32_BLOB(512)` vector per **candidate** row of `transactions`/`notifications`/`emails` (plus `embedding_model`, `gemini-embedding-001/512`), so "parecidos a este" is a pure-SQL cosine scan that works **offline** — the vector of the row on screen is already stored. Only the sweep needs the network (`POST /embed` on the finance worker, same `auth_finance` cookie; the worker returns vectors and **never writes** to the user's Turso, so the device stays the only writer), and it sits behind "Vectorizar pendientes" in `ProfileScreen`; it writes after every batch so it can be cut off and resumed. One type and one dimensionality across the three tables is what makes the **cross-table** search work (`vector_distance_cos` wants matching type/dims), which is the point: a transaction's neighbouring notifications/emails each get a "Vincular" that writes `transaction_sources`, collecting labelled examples for the classification batch while the app is used. **No vector index** — the sync engine has `vector32`/`vector_distance_cos`/`vector_extract` but not `libsql_vector_idx`/`vector_top_k`, and the index DDL does not even parse on-device. Canonical text: transactions are written payee-first and sentence-shaped (`payee · origen → destino · nota`, **no amount, no date** — that is `Reconcile`'s job and in a vector it is noise) precisely so they sit in the same register as a push alert; getting that wrong makes the cross-table search look like proof that vectors don't work. The amount is **not** embedded and instead **re-ranks**: the model has no notion of magnitude (`$46.210` tokenizes closer to `$462.100` than to `$46.500`), so `similar()` over-fetches by cosine and re-sorts by `distance + 0.35 * |ln(a/b)|` — log-ratio, so it is scale-free, clamped at 1, zero when either side has no amount or the commodities differ (never a guess). The money of a notification/email comes from `biggestMoney` (the largest `MONEY_TEXT` mention; the smaller numbers around it are balances and card digits), which is also what puts an amount next to those rows in the list — the human confirming a link has to see the money and the day, because cosine only ever says "these read alike". Candidates are the rows that pass `hasAmount` (`MONEY_TEXT`, currency-anchored on **both** sides), with `EmbeddingsRepository.embedOne` behind a per-row "buscar parecidas" button as the escape hatch when the prefilter is wrong. Screens: `NotificationDetailScreen` (new; `NotificationCard` is now clickable), plus sections on `TransactionDetailScreen` and `EmailDetailScreen`. Desktop harness: `FakeEmbedder` (hashed bag-of-words, non-semantic) + `registerVectorFunctions` in `FakeVectors.kt`, which implements the three vector functions as sqlite-jdbc user functions — `./gradlew :app:desktopApp:shot -Pshot.route=notification`.
- Notification/email ingestion (`Ingest.kt` + `IngestRepository`, sharedLogic commonMain, pure + deterministic): `parseNotification`/`parseEmail` recognize movements with an **allowlist of bank templates** and map them to the same `ImportCandidate` the document importer produces, mapping them to the same `ImportCandidate` the document importer produces. The screen that reviewed them (Home overflow → «Detectar movimientos», `InboxReviewRoute`) is **gone**: notifications are now recorded automatically on arrival (see the auto-record entry above), so `IngestRepository.inbox()` currently has no caller in the app — the templates live on as the deterministic half of the web inspector (`WebBridge.kt`) and as the net under a future email path. Allowlist, never a blocklist: on the 21.383 captured notifications of the dev device, the ones containing a `$` are overwhelmingly promotions ("¡15% OFF en Carrefour! Compra mínima: $15.000" has amount, merchant and verb), so only a known sentence counts — 22 movements, no false positives, plus 27 in 125 mails. Rules are scoped by package/sender, amounts parse es-AR grouping (`$ 19200`, `$8.000`, `U$S100,00`), and emails need `decodeMimeHeader` (RFC 2047) + `emailPlainText` (quoted-printable, `<style>` blocks dropped, tags stripped) — read from `body_html` first because the stored text part is frequently raw MIME truncated at 10 kB with the receipt past the cut. `resolveAccountHint` maps an app/card name onto the user's tree conservatively (commodity breaks "Santander Pesos" vs "Dolares"; a non-unique winner returns null and the screen's default applies). `IngestRepository.inbox()` scans a 30-day window and drops refs already in `transaction_sources` (`knownSourceRefs`), so a message stops being offered once it is linked. It never writes: everything goes through the review screen.
- WhatsApp entry (`app/wa-bridge` + `app/worker/src/whatsapp.ts`): you message a bot number («panadería 300») and the transaction is written straight to the ledger. The protocol needs a permanently open authenticated websocket (keepalives every 20–30 s) plus a live Signal store, so it is the **only piece that cannot live on Cloudflare**: a ~300-line Go bridge (whatsmeow, pure Go, no cgo) runs on Fly (`weil-wa-bridge`, `iad`, one machine, **no public IP** — admin endpoints `/pair`, `/send`, `/health` are reached with `fly proxy 8080 -a weil-wa-bridge`) and forwards each message, HMAC-signed, to the worker, which owns every decision; the response's `reply` is what the bot says back. whatsmeow's session store is the `wa-bridge` Turso database in the **finance** group (`libsql-client-go` is pure Go and supports the interactive transactions `store/sqlstore` needs — D1 cannot back it, its HTTP API only takes batches sent up front), which makes the container stateless: redeploying or moving hosts never re-pairs. Linking a user is inverted on purpose — the app never asks for a phone number: `POST /whatsapp/link` mints a short code into `whatsapp_link_codes` (shared D1, created lazily like `ensureEmailColumns`) and the number proves itself by *sending* «vincular ABC123»; unknown numbers get silence, not an error, so the bot is not an oracle for "is this number registered". Writes are idempotent on `transaction_sources(kind='whatsapp', ref=<message id>)` (checked before anything else) and carry a `CandidateEvent.eventKey`-shaped fingerprint, so `Reconcile.kt` sees the bank's push notification for the same purchase as a `Duplicate`; `deshacer` drops the last one within 24 h. Gotchas: a single-connection pool **deadlocks** whatsmeow (it reads a row set and writes in the same call path — the symptom is a silent hang with 0 prekeys uploaded, so no one can open a Signal session and messages simply never arrive); a direct chat now arrives addressed by **LID** (`2817649578196@lid`), so filtering on `types.DefaultUserServer` drops every real message and the phone number for the link lookup must come from `Info.SenderAlt`; Fly creates **two** machines by default, which would be two clients on one device session, hence `count = 1` + `strategy = "immediate"`. Reading the message is Gemini's (`interpretWithGemini`), and deliberately so: the amount, the direction, the payee and the accounts named are language ("veinte mil pesos", `1.234,56`, `20k`, "pasé X de A a B"), and a regex deciding whether `12.500` is twelve thousand or twelve-fifty is a heuristic hiding in the plumbing. The chat path reorders `GEMINI_MODELS` to try the lite model first (a one-line message measured ~55 s on the full model, ~2 s on lite). The **category** is the one part that is not language but a pick from the user's own tree, so it is a TypeSafe Choice (`app/worker/src/chat.ts`) issued with `Promise.all` *beside* the Gemini call — free in wall clock — asking the expense and the income question speculatively and keeping whichever the direction turned out to be (a transfer uses neither: its "category" is the destination account). The question is **imported from `suggest.ts`**, so the typing screen and the bot share one definition of "which category is this". It wins when it answers, and Gemini's own guess stays in the prompt as the fallback, which covers both a TypeSafe outage and the honest declines («plazo fijo 15300» → ninguna at 0.40 confidence). Measured with `bun scripts/chat.ts` in `prueba-jev` (importing the worker's questions, so the harness cannot drift): 16/17, p50 ~305 ms — comfortably under the Gemini call it rides along with.
- Web app (`app/web`, worker `finance-web` at **https://finance.fausto.ar**): SvelteKit + adapter-cloudflare SPA, passkey sign-in against the same auth worker (no register fallback), **read-only** over the user's own Turso DB straight from the browser with the session JWT (`ReadOnlyDb` refuses any statement that doesn't start with `select`; writes stay in the phone app, which owns the transaction boundaries and the undo). Screens: captured notifications/emails with keyset pagination and template-similarity grouping (`src/lib/similar.ts` — masks amounts/dates/codes so "same bank template" is a deterministic signature, used to harvest examples for new `Ingest.kt` rules), the accounts tree, and the import/ingest inspectors, which run the **real** logic: `/api/analyze` imports the production functions from `app/worker/src/import.ts`, and ingest/reconcile run the actual Kotlin compiled to JS from `:app:sharedLogic` via `WebBridge.kt` (JSON in, JSON out) rather than a TS port. Gotcha: this hostname is also the passkey rp id, and a hostname belongs to exactly one Worker — the auth worker still owns `/.well-known/assetlinks.json`, both Apple app-site-association paths and `/desktop-pair`, so `src/hooks.server.ts` proxies them to `auth.fausto.ar` with `?rp=finance.fausto.ar` (the auth worker picks its app by request host, which is why the override exists). If those four paths stop resolving, native passkey sign-in breaks.
- Android notification listener: `WeilNotificationListener` (sharedLogic androidMain, declared in androidApp manifest with `BIND_NOTIFICATION_LISTENER_SERVICE`; `QUERY_ALL_PACKAGES` is used by the PackageManager enrichment in `AppLookup.kt` — label/`FLAG_SYSTEM`/PNG icon captured at first sighting). It captures every posted notification (no filtering), writes it via `NotificationsRepository.record` (which returns the new row id — the silent suggestion run described above keys off it) and syncs throttled: max one `sync()` per 30 s with a trailing sync after a burst; sync failures are swallowed (rows stay local until the next sync; `NotificationsScreen.list()` always syncs before reading). Live UI refresh comes from `NotificationsRepository.changes` (SharedFlow).
- Sync chains: every device joins the user's account with its own passkey via the auth worker's chain endpoints (`ChainRepository` — list/invite/approve/request/join; cookie-authed like `session/refresh`). `ProfileScreen` manages the chain via `ChainState` (device list, invite QR with countdown, scanner-based approve, two-step revoke); revoking rotates the user's Turso tokens, so `ChainRepository.revoke` proactively calls `auth.refresh()` (or `signOutLocal()` when revoking the current device). New devices pair from the login screen ("Pair with an existing account"): scan an invite QR, or show a request QR and poll until approved — both end in two-phase `chain/join` via `AuthRepository.joinChain` (passkey `create()` ceremony, then the register-shaped token payload). QR rendering is qrose (`rememberQrCodePainter`); QR *scanning* is `QrScanner` (expect/bridge, lazily resolved like passkeys because it needs a foreground activity): Android = Google code scanner (`play-services-code-scanner`, no camera permission, `barcode_ui` meta-data in the androidApp manifest), iOS = `QrScannerManager.swift` (VisionKit `DataScannerViewController`, camera prompt handled by the bridge, `NSCameraUsageDescription` in the iosApp Info.plist). `ChainLink.parse` validates scanned URLs against `AuthConfig.SLUG` before any API call.

Android DB is the new Turso sync engine (`turso` monorepo, `turso_sync_sdk_kit` crate `0.8.0-pre.8`): a vendored `libturso_sync_sdk_kit.so` (4 ABIs, 16 KB-aligned — Google Play page-size requirement) in `app/sharedLogic/src/androidMain/jniLibs/`, driven from Kotlin over JNA interface mapping (`ar.fausto.weil.TursoNative`). The engine's sync IO is caller-driven: `AndroidDatabase.drainOperation` pumps `turso_sync_operation_resume` until DONE and services the IO queue (HTTP via OkHttp with `Authorization: Bearer <jwt>` injected, atomic file read/write of sync metadata). Rebuild instructions: `app/sharedLogic/src/androidMain/jniLibs/README.md` (nix develop → cargo ndk).

iOS runs the *same* engine/commit through Kotlin/Native cinterop instead of JNA: the Rust **staticlib** (`libturso_sync_sdk_kit.a`, `aarch64-apple-ios` + `-sim`) is built by `scripts/build-turso-ios.sh` into `app/sharedLogic/src/iosMain/nativeLibs/<kmpTarget>/` (~170 MB each, gitignored), bound by `app/sharedLogic/src/nativeInterop/cinterop/turso.def` against the headers Android already vendors, and driven by `IosTursoDatabase` (`TursoDatabase.ios.kt`) — a straight port of `AndroidDatabase` where the IO pump does HTTP with NSURLSession (blocking on a dispatch semaphore, fine because it runs on `DbDispatcher`) and atomic writes with `NSData.writeToFile(atomically = true)`. Because all sync HTTP now goes through NSURLSession, the Rust rustls stack is never used on iOS — which is what used to fail with "TLS error: no valid native root CA certificates found (0 invalid)" (`rustls-native-certs` takes its unix branch on iOS and finds no cert store; libsql-swift 0.3.2's prebuilt lib ignored the `webpki` desc flag on device, verified byte-wise).

Gotchas:
- Named params MUST use `:name` placeholders with map keys including the leading colon (`":name"`); `turso_statement_named_position` requires the prefix, and an unknown name silently binds nothing (verified 1-indexed positions on host smoke test).
- All DB calls (both engines) must run on the 16MB-stack dispatcher (`dbDispatcher` on Android, `DbDispatcher` on iOS) — the Rust parser overflows coroutine stacks otherwise. On Android the native work is deferred to first use (inside `DatabaseProvider.use`) so it never runs off-dispatcher; `AndroidDatabase_init` is cheap.
- Old libsql replica files (`local.db*`) are deleted on first open of the new engine (both platforms) — replicas were pull-only copies, the server is the source of truth.
- **`alter table ... rename to` is local-only on the sync engine**: it applies to the local file, `sync()` returns OK, and the rename is never pushed — the device diverges from the server silently and forever (verified on-device against a scratch database; `create table`, `create index`, `insert ... select` and `drop table` all replicate normally). Renaming a table therefore means copy-and-drop, which is what `migrateLegacyTransactionsTable()` in `Schema.kt` does for `ledger_transactions` -> `transactions` — it runs **before** `SCHEMA_SQL` (whose `create table if not exists transactions` would otherwise create an empty table and strand every row under the old name) and before the `user_version` short-circuit, so it also heals the ghost table an un-updated device recreates and writes into. Two devices migrating offline converge because the copy is `insert or ignore` on the primary key. Dropping a table that still holds unsynced row changes makes the next push fail to render them (`SQL_PARSE_ERROR: near RP, "None"`, recovers on the following sync), hence the best-effort `sync()` before the drop.
- `migrateSchema()`'s `alter table add column` calls go through `addColumn()`, which swallows "duplicate column name": the `pragma table_info` guard reads local state that can lag behind the primary.
- Android passkeys need `assetlinks.json` with **both** `delegate_permission/common.get_login_creds` and `delegate_permission/common.handle_all_urls`, plus an `asset_statements` `<meta-data>` in `AndroidManifest.xml` pointing to the file.
- iOS needs the AASA file; both association files are served by the auth worker from the `finance` app's `android`/`ios` config.
- The auth worker's WebAuthn verification must include the Android APK key-hash origin (`android:apk-key-hash:<base64url(sha256(cert))>`) in `expectedOrigin`, because native Android responses use that instead of `https://finance.fausto.ar`.
- `AccountActionsSheet` hides its own sheet before showing rename/move and calls `onDismiss` only when the flow ends — callers remove it on dismiss, which would otherwise drop the dialog.
- Kotlin exception classes can't be thrown from Swift as `Error`; the Swift bridge throws NSErrors whose localizedDescription contains "passkey cancelled"/"passkey not found", translated by `bridgedPasskeys()` in `IosAuth.kt`.
