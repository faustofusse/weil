## Architecture

Auth is passkey-based via the auth worker in `/Users/fausto/sw/auth` (deployed at https://auth.fausto.ar, app slug `finance`, rp domain `finance.fausto.ar`). Flow: `AppGraph` (commonMain) wires `AuthRepository` (login→fallback register via `PasskeyCeremony`), `DatabaseProvider` (jwt → `session/refresh` on `401`/`unauthorized` in error text → re-login on 401), `AccountsRepository` and `NotificationsRepository`. Each user gets their own Turso DB provisioned by the worker (libsql-type on Turso Cloud); local synced replicas live at `databases/{userId}/turso.db` (Android filesDir; iOS still uses the old libsql embedded replica at `databases/{userId}/local.db` via libsql-swift). Tokens + the `auth_finance` refresh cookie are in secure storage (EncryptedSharedPreferences / iOS Keychain via the Swift `KeychainStore` bridge). iOS passkey ceremony + secure store are Swift (`PasskeyManager.swift`, `KeychainStore.swift`) injected into `IosBridges` before `MainViewController()` runs; `AppGraph` takes `passkeys: () -> PasskeyCeremony` lazily (Android builds the ceremony around the foreground activity only when sign-in starts).

Auth is passkey-based; Android `WeilApplication` (app class in the manifest) owns the single `AppGraph` shared by `MainActivity` and the notification listener service (`AndroidGraphHolder`). The old finance app lives in `/Users/fausto/sw/finance` — its UI (Home/Notifications screens, FinanceTheme, NavDisplay transitions) and notification listener were ported almost verbatim.

- UI (sharedUI commonMain): Navigation 3 KMP (`org.jetbrains.androidx.navigation3:navigation3-ui`) with a plain `mutableStateListOf<Any>` back stack and the old slide/fade transition specs. Theme: the catalog is the `AppTheme` enum in `AppTheme.kt` (one entry = one complete M3 `ColorScheme`; adding/swapping a theme touches only that file); `Theme.kt` holds `AppThemeState` + `LocalAppThemeState` (runtime swap with one assignment) and `FinanceTheme(theme)` wraps all of `RootScreen`, splash included. Screens must read colors only via `MaterialTheme.colorScheme.*` — no top-level color vals (exception: the QR card's white backing, needed for scanner contrast). Screens: `HomeScreen` (notification access status, hidden on iOS — `notificationAccess` expect/actual is null there), `NotificationsScreen` (exact old layout minus the per-row synced icon), `AccountsScreen` (accounts CRUD). The few Material icons are hand-built in `Icons.kt` (CMP icons artifacts are frozen at 1.7.3); PNG app icons decode via `decodeIcon` expect/actual (BitmapFactory on Android, Skia elsewhere).
- Schema: single `SCHEMA_SQL` const in commonMain `Schema.kt`, applied idempotently on every open on both engines (accounts, notifications, applications indexed by post_time). All timestamps are epoch **ms** — the email worker (`app/worker`) writes `emails.received_at` server-side, so it must also use ms (`Date.now()`), and SCHEMA_SQL carries an idempotent seconds→ms migration for older rows. No device_id/modified_at/deleted_at/synced_at columns — the Turso engine replicates row state (incl. deletes) between devices.
- Android notification listener: `WeilNotificationListener` (sharedLogic androidMain, declared in androidApp manifest with `BIND_NOTIFICATION_LISTENER_SERVICE`; `QUERY_ALL_PACKAGES` is used by the PackageManager enrichment in `AppLookup.kt` — label/`FLAG_SYSTEM`/PNG icon captured at first sighting). It captures every posted notification (no filtering, like the old app), writes it via `NotificationsRepository.record` and syncs throttled: max one `sync()` per 30 s with a trailing sync after a burst; sync failures are swallowed (rows stay local until the next sync; `NotificationsScreen.list()` always syncs before reading). Live UI refresh comes from `NotificationsRepository.changes` (SharedFlow).
- Sync chains: every device joins the user's account with its own passkey via the auth worker's chain endpoints (`ChainRepository` — list/invite/approve/request/join; cookie-authed like `session/refresh`). `ProfileScreen` manages the chain via `ChainState` (device list, invite QR with countdown, scanner-based approve, two-step revoke); revoking rotates the user's Turso tokens, so `ChainRepository.revoke` proactively calls `auth.refresh()` (or `signOutLocal()` when revoking the current device). New devices pair from the login screen ("Pair with an existing account"): scan an invite QR, or show a request QR and poll until approved — both end in two-phase `chain/join` via `AuthRepository.joinChain` (passkey `create()` ceremony, then the register-shaped token payload). QR rendering is qrose (`rememberQrCodePainter`); QR *scanning* is `QrScanner` (expect/bridge, lazily resolved like passkeys because it needs a foreground activity): Android = Google code scanner (`play-services-code-scanner`, no camera permission, `barcode_ui` meta-data in the androidApp manifest), iOS = `QrScannerManager.swift` (VisionKit `DataScannerViewController`, camera prompt handled by the bridge, `NSCameraUsageDescription` in the iosApp Info.plist). `ChainLink.parse` validates scanned URLs against `AuthConfig.SLUG` before any API call.

Android DB is the new Turso sync engine (`turso` monorepo, `turso_sync_sdk_kit` crate `0.8.0-pre.8`): a vendored `libturso_sync_sdk_kit.so` (4 ABIs, 16 KB-aligned — Google Play page-size requirement) in `app/sharedLogic/src/androidMain/jniLibs/`, driven from Kotlin over JNA interface mapping (`ar.fausto.weil.TursoNative`). The engine's sync IO is caller-driven: `AndroidDatabase.drainOperation` pumps `turso_sync_operation_resume` until DONE and services the IO queue (HTTP via OkHttp with `Authorization: Bearer <jwt>` injected, atomic file read/write of sync metadata). Rebuild instructions: `app/sharedLogic/src/androidMain/jniLibs/README.md` (nix develop → cargo ndk).

Gotchas:
- Named params MUST use `:name` placeholders with map keys including the leading colon (`":name"`); `turso_statement_named_position` requires the prefix, and an unknown name silently binds nothing (verified 1-indexed positions on host smoke test).
- All DB calls (both engines) must run on the 16MB-stack dispatcher (`dbDispatcher` on Android, `DbDispatcher` on iOS) — the Rust parser overflows coroutine stacks otherwise. On Android the native work is deferred to first use (inside `DatabaseProvider.use`) so it never runs off-dispatcher; `AndroidDatabase_init` is cheap.
- Old libsql replica files (`local.db*`) are deleted on first open of the new engine — replicas are pull-only copies, the server is the source of truth.
- Android passkeys need `assetlinks.json` with **both** `delegate_permission/common.get_login_creds` and `delegate_permission/common.handle_all_urls`, plus an `asset_statements` `<meta-data>` in `AndroidManifest.xml` pointing to the file.
- Android passkeys need `assetlinks.json` with **both** `delegate_permission/common.get_login_creds` and `delegate_permission/common.handle_all_urls`, plus an `asset_statements` `<meta-data>` in `AndroidManifest.xml` pointing to the file.
- iOS needs the AASA file; both association files are served by the auth worker from the `finance` app's `android`/`ios` config.
- The auth worker's WebAuthn verification must include the Android APK key-hash origin (`android:apk-key-hash:<base64url(sha256(cert))>`) in `expectedOrigin`, because native Android responses use that instead of `https://finance.fausto.ar`.
- Kotlin exception classes can't be thrown from Swift as `Error`; the Swift bridge throws NSErrors whose localizedDescription contains "passkey cancelled"/"passkey not found", translated by `bridgedPasskeys()` in `IosAuth.kt`.
