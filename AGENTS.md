## Architecture

Auth is passkey-based via the auth worker in `/Users/fausto/sw/auth` (deployed at https://auth.fausto.ar, app slug `finance`, rp domain `finance.fausto.ar`). Flow: `AppGraph` (commonMain) wires `AuthRepository` (login→fallback register via `PasskeyCeremony`), `DatabaseProvider` (jwt → `session/refresh` on `401`/`unauthorized` in error text → re-login on 401), `AccountsRepository` and `NotificationsRepository`. Each user gets their own Turso DB provisioned by the worker (libsql-type on Turso Cloud); local synced replicas live at `databases/{userId}/turso.db` (Android filesDir; iOS still uses the old libsql embedded replica at `databases/{userId}/local.db` via libsql-swift). Tokens + the `auth_finance` refresh cookie are in secure storage (EncryptedSharedPreferences / iOS Keychain via the Swift `KeychainStore` bridge). iOS passkey ceremony + secure store are Swift (`PasskeyManager.swift`, `KeychainStore.swift`) injected into `IosBridges` before `MainViewController()` runs; `AppGraph` takes `passkeys: () -> PasskeyCeremony` lazily (Android builds the ceremony around the foreground activity only when sign-in starts).

Auth is passkey-based; Android `WeilApplication` (app class in the manifest) owns the single `AppGraph` shared by `MainActivity` and the notification listener service (`AndroidGraphHolder`). `AppGraph` exposes `accounts` (`AccountsRepository`) and `ledger` (`TransactionsRepository`) for the double-entry bookkeeping layer.

- UI (sharedUI commonMain): Navigation 3 KMP (`org.jetbrains.androidx.navigation3:navigation3-ui`) with a plain `mutableStateListOf<Any>` back stack and the slide/fade transition specs. Theme: the catalog is the `AppTheme` enum in `AppTheme.kt` (one entry = one complete M3 `ColorScheme`; adding/swapping a theme touches only that file); `Theme.kt` holds `AppThemeState` + `LocalAppThemeState` (runtime swap with one assignment) and `FinanceTheme(theme)` wraps all of `RootScreen`, splash included. Screens must read colors only via `MaterialTheme.colorScheme.*` — no top-level color vals (exception: the QR card's white backing, needed for scanner contrast). All UI strings are centralized: Spanish is the base locale in `sharedUI/src/commonMain/composeResources/values/strings.xml`; screens read them via `stringResource(Res.string.*)` (never hardcode text) — adding a language later is one sibling `values-xx/strings.xml`. Strings needed inside non-composable callbacks are captured in vals during composition; `ChainState` messages are passed pre-formatted from the composable layer, while repository exception text (sharedLogic) stays untranslated (developer-facing). Screens: `HomeScreen` (one LazyColumn: per-commodity net worth header, **Asset accounts only** under the "Cuentas" `SectionHeader` with a + button for the add-asset-account dialog, expand/collapse chevrons with hoisted expansion state, then the last 5 transactions grouped into one card per day (the journal's `DayHeader` + the compact one-line `TransactionRow`: payee, dim "origen → destino" leaf names, single signed amount colored only when the user's own money moved — see `flowOf`) with "Ver todo"; both `SectionHeader`s share the same metrics, their trailing action pinned to 32.dp; pull-to-refresh; long-press bottom sheet for rename/move/delete with Snackbar undo via `Feedback.undoable` — `LedgerUi.kt` mounts the host in `RootScreen`; top bar = Journal, Profile and an overflow with tree/notifications/emails; extended FAB opens `TransactionQuickRoute(Expense)` directly), `AccountsTreeScreen` (the complete tree of every type with per-type headers/totals + FAB for the add dialog with type picker; shared tree-row components — `NodeRowView`, `AccountActionsSheet`, `AddAccountDialog` — live in `AccountsTreeScreen.kt` as `internal`), `TransactionQuickScreen` (simplified entry: segmented Gasto/Ingreso/Traspaso switcher (switching keeps the asset pick), autofocused amount with live validation, two typed pickers with per-kind labels, description, sticky record bar; category creation inline for Gasto, commodity fixed ARS and date = now; drafts carry kind-driven signs: gasto asset −X/expense +X, ingreso income −X/asset +X, traspaso from −X/to +X), `JournalScreen` (day-grouped transaction cards via `dayGroup()`/`DayGroup` value object, localized via `dayLabel()` + the `weekdays_short`/`months_short` string-arrays, pull-to-refresh and infinite scroll), `TransactionEditScreen` (full ledger editor: payee-first, M3 date picker, stacked posting rows with FilterChip commodities + decimal keyboard, sticky record bar with live per-commodity residual check, delete with Snackbar undo), `AccountDetailScreen` (register under day headers with running balance, subtree chip only for parent accounts, overflow opens `AccountActionsSheet`, reloads on `ledger.changes`, infinite scroll, prefill FAB), `NotificationsScreen`, `EmailsScreen`, `ProfileScreen`. Account picking is `AccountPickerSheet` (searchable ModalBottomSheet, indented tree when unfiltered, flat paths while searching; optional `createLabel`/`onCreate` row adds inline creation for expense categories). Underlying linkages: `TransactionNewRoute(accountId)` pre-fills the first posting on any screen. `TransactionsRepository.get(id)` fetches one transaction for edit/undo. `AccountsRepository.add` returns the created id. The few Material icons are hand-built in `Icons.kt` (CMP icons artifacts are frozen at 1.7.3); PNG app icons decode via `decodeIcon` expect/actual (BitmapFactory on Android, Skia elsewhere).
- Schema: single `SCHEMA_SQL` const in commonMain `Schema.kt`, applied idempotently on every open on both engines, followed by `migrateSchema()` for non-idempotent column additions. Tables: `accounts(id, name, parent_id, type)`, `ledger_transactions(id, date, payee, note, source_notification_id, source_email_id, created_at)`, `postings(id, transaction_id, account_id, amount_minor, commodity)`, `ledger_transactions.source_document_id` (R2 hash of an AI-imported document), plus `notifications`, `applications`, `emails`. All timestamps are epoch **ms** — the email worker (`app/worker`) writes `emails.received_at` server-side, so it must also use ms (`Date.now()`), and SCHEMA_SQL carries an idempotent seconds→ms migration for older rows. No device_id/modified_at/deleted_at/synced_at columns — the Turso engine replicates row state (incl. deletes) between devices. `migrateSchema()` also seeds default accounts **only when the accounts table is empty** (never resurrects user deletions): "External" expense and income accounts with fixed ids `EXTERNAL_EXPENSE_ID`/`EXTERNAL_INCOME_ID` (fixed ids so two concurrently-seeded fresh devices converge on the same synced rows) — these are the defaults in `TransactionQuickScreen` (gasto category / ingreso source), matched by `EXTERNAL_ACCOUNT_NAME`.
- Document import (AI): the user shares an image/PDF into the app (Android `ACTION_SEND` filter on `MainActivity`, `singleTask`; `handleSharedDocument` reads the `content://` stream and parks it in `SharedImportInbox`, which `RootScreen` replays once composed and signed in) or picks one from Home's overflow (`DocumentPicker` — SAF on Android, `UIDocumentPickerViewController` via `DocumentPickerManager.swift` on iOS, AWT `FileDialog` on desktop; resolved lazily like `QrScanner` because it needs a foreground activity). `ImportRepository.analyze` POSTs the raw bytes to the finance worker (`api.finance.fausto.ar/import/analyze`) with the same `auth_finance` cookie the auth worker issues — the worker re-implements `requireAuth` against the shared `AUTH_DB`, so revocation/expiry are free. The worker stores the file in R2 (`finance-docs`, key `{userId}/{sha256}`, readable back via `GET /import/document/{docId}`), loads the user's postable accounts from their Turso DB (**parents included** — the tree is organizational and postings may reference any node, so filtering to leaves silently hid "Comida" as soon as it grew a "Comida:Verduras" child; expense/income as categories **and** asset/liability as payment methods, so "Forma de Pago: Dinero disponible en Mercado Pago" resolves to the user's own Mercado Pago account — per-candidate `accountId`, falling back to the review screen's default account), and calls **Gemini** with `responseSchema` structured output — through the account's AI Gateway, falling back to the Google API directly when the gateway answers with an `AiGatewayError`. `GEMINI_MODELS` is an ordered list (`gemini-3.5-flash,gemini-3.6-flash,gemini-3.5-flash-lite`): a 503/429 "high demand" on one pool moves to the next model rather than retrying the same one, which can stay congested for minutes. It returns candidates only; `ImportReviewScreen` (compact rows, tap to expand and edit payee/amount/category, checkbox to approve) writes them in one SQL transaction via `TransactionsRepository.addAll`, tagged with `source_document_id` and undoable from the Snackbar; the screen-wide default account (used only for rows the document didn't attribute to one of the user's own accounts) seeds from the mode of the candidates' detected accounts, a lone candidate opens pre-expanded, and `imePadding()` sits on the `Scaffold` (not the inner content) so the sticky bottom bar rides above the keyboard. Analysis of a one-page statement takes ~15–25 s, so `ImportRepository`'s client installs `HttpTimeout` with a 180 s budget (the default socket timeout kills the call otherwise). Gotchas: `gemini-2.5-flash` is retired for new API keys; the screen depends on the `DocumentAnalyzer` interface so the desktop shot harness can inject `FakeImportAnalyzer` (`./gradlew :app:desktopApp:shot -Pshot.route=import`).
- Android notification listener: `WeilNotificationListener` (sharedLogic androidMain, declared in androidApp manifest with `BIND_NOTIFICATION_LISTENER_SERVICE`; `QUERY_ALL_PACKAGES` is used by the PackageManager enrichment in `AppLookup.kt` — label/`FLAG_SYSTEM`/PNG icon captured at first sighting). It captures every posted notification (no filtering), writes it via `NotificationsRepository.record` and syncs throttled: max one `sync()` per 30 s with a trailing sync after a burst; sync failures are swallowed (rows stay local until the next sync; `NotificationsScreen.list()` always syncs before reading). Live UI refresh comes from `NotificationsRepository.changes` (SharedFlow).
- Sync chains: every device joins the user's account with its own passkey via the auth worker's chain endpoints (`ChainRepository` — list/invite/approve/request/join; cookie-authed like `session/refresh`). `ProfileScreen` manages the chain via `ChainState` (device list, invite QR with countdown, scanner-based approve, two-step revoke); revoking rotates the user's Turso tokens, so `ChainRepository.revoke` proactively calls `auth.refresh()` (or `signOutLocal()` when revoking the current device). New devices pair from the login screen ("Pair with an existing account"): scan an invite QR, or show a request QR and poll until approved — both end in two-phase `chain/join` via `AuthRepository.joinChain` (passkey `create()` ceremony, then the register-shaped token payload). QR rendering is qrose (`rememberQrCodePainter`); QR *scanning* is `QrScanner` (expect/bridge, lazily resolved like passkeys because it needs a foreground activity): Android = Google code scanner (`play-services-code-scanner`, no camera permission, `barcode_ui` meta-data in the androidApp manifest), iOS = `QrScannerManager.swift` (VisionKit `DataScannerViewController`, camera prompt handled by the bridge, `NSCameraUsageDescription` in the iosApp Info.plist). `ChainLink.parse` validates scanned URLs against `AuthConfig.SLUG` before any API call.

Android DB is the new Turso sync engine (`turso` monorepo, `turso_sync_sdk_kit` crate `0.8.0-pre.8`): a vendored `libturso_sync_sdk_kit.so` (4 ABIs, 16 KB-aligned — Google Play page-size requirement) in `app/sharedLogic/src/androidMain/jniLibs/`, driven from Kotlin over JNA interface mapping (`ar.fausto.weil.TursoNative`). The engine's sync IO is caller-driven: `AndroidDatabase.drainOperation` pumps `turso_sync_operation_resume` until DONE and services the IO queue (HTTP via OkHttp with `Authorization: Bearer <jwt>` injected, atomic file read/write of sync metadata). Rebuild instructions: `app/sharedLogic/src/androidMain/jniLibs/README.md` (nix develop → cargo ndk).

Gotchas:
- Named params MUST use `:name` placeholders with map keys including the leading colon (`":name"`); `turso_statement_named_position` requires the prefix, and an unknown name silently binds nothing (verified 1-indexed positions on host smoke test).
- All DB calls (both engines) must run on the 16MB-stack dispatcher (`dbDispatcher` on Android, `DbDispatcher` on iOS) — the Rust parser overflows coroutine stacks otherwise. On Android the native work is deferred to first use (inside `DatabaseProvider.use`) so it never runs off-dispatcher; `AndroidDatabase_init` is cheap.
- Old libsql replica files (`local.db*`) are deleted on first open of the new engine — replicas are pull-only copies, the server is the source of truth.
- Android passkeys need `assetlinks.json` with **both** `delegate_permission/common.get_login_creds` and `delegate_permission/common.handle_all_urls`, plus an `asset_statements` `<meta-data>` in `AndroidManifest.xml` pointing to the file.
- iOS needs the AASA file; both association files are served by the auth worker from the `finance` app's `android`/`ios` config.
- The auth worker's WebAuthn verification must include the Android APK key-hash origin (`android:apk-key-hash:<base64url(sha256(cert))>`) in `expectedOrigin`, because native Android responses use that instead of `https://finance.fausto.ar`.
- `AccountActionsSheet` hides its own sheet before showing rename/move and calls `onDismiss` only when the flow ends — callers remove it on dismiss, which would otherwise drop the dialog.
- Kotlin exception classes can't be thrown from Swift as `Error`; the Swift bridge throws NSErrors whose localizedDescription contains "passkey cancelled"/"passkey not found", translated by `bridgedPasskeys()` in `IosAuth.kt`.
